# 从一次复审看懂 claude-web-api

假设你正让一个本地 agent 改支付回调，测试已经通过，但错误分支是否吞掉重试仍然拿不准。你想再听一次 Claude 的判断，又不想把仓库、终端历史和登录凭据复制到网页里。更麻烦的是，如果发送超时，你无法确认网页到底有没有收到消息；再点一次可能得到两份互相矛盾的回复。

这个项目把这类「再问一次」变成可以核对的回路。它不替你执行代码，也不替你决定何时咨询。你先划定授权范围，宿主整理必要的路径、证据和问题，桥接使用本机已登录的 Chrome 提交并读取回复，最后把会话状态与结果交还宿主。下面沿三步走：先看一个最小回路，再补上连续追问和不确定发送，最后决定它是否适合你的场景。

画面：左侧是当前宿主，中间是本地桥接与自有后台标签页，右侧是 Claude 网页会话；三条箭头依次是「授权上下文」「一次提交」「结构化结果 + 别名」。

## 先让一次提问有据可查

假设你用同一个别名 `payment-review` 问一句话：请只审查错误分支，并列出可证伪点。CLI、MCP 工具或 `claude` 技能都能发起这次请求，差别只是入口；真正相同的部分是桥接如何工作。

桥接先连接 loopback 上的 Chrome 调试端口，再打开自有后台标签页。它不复制浏览器 cookie，也不在 Node 侧伪装请求头；请求发生在 claude.ai 页面上下文里，沿用你已有的登录态。老式纯文本会话可经 REST 与 SSE 读取回复；升级后的网页会话和附件走原生编辑器。不同代网页实现并存，因此代码必须按页面实际状态选路，不能把一条请求形状当成永久契约。

这一步只新增一个机制：**提交与读取由同一条本地路径负责**。最小验证不是相信一行「成功」，而是读取同一别名的 transcript：里面应有一条 human 消息、对应回复以及终止状态。若返回 `complete: false`，内容已经终止但被截断；这与「发送成功」是两件事。网页会话可能变化，所以这条路径的价值是留下可核对的状态，不是承诺网页接口永远不变。

一次提问仍然漏掉一件事：复审通常不会一轮结束。

## 再加连续追问与状态

现在宿主执行了建议，新增一条失败测试，需要把新证据交给同一个 Claude 会话。桥接用别名找到服务端当前分支，再把追问接到已完成的叶节点之后；CLI、MCP 与插件共享别名状态，因此不必把整段旧聊天复制进新请求。这里的「分支」可以理解为聊天树里当前采用的一条路径，它不是 Git 分支，也不是本地凭空拼接的历史。

这一步新增的机制是**会话状态**。它解决了两类误判：第一，追问能看到上一轮上下文；第二，超时后能先回读服务端历史，再判断这次提交是否真的落地。发送结果不确定时，桥接保留 `pending`，绝不自动重发。只有权威历史证明原问题与已完成回复成对出现，恢复才清除 pending；备用 HTTP 通道没有同等权威历史，因此放弃未确认尝试必须显式确认。

这种设计把「回复终止」与「内容完整」拆开。`complete: false` 可以保留并供后续追问，而 `pending` 保护的是「是否已发送」这个更早的问题。锁、并发写入和安装记录用的也是同一思路：状态先落盘，动作再提交，失败时保留恢复路径。

【图 2|超时后的两个分叉】
画面：上半支为「服务端历史确认完成 → 清除 pending → 继续追问」；下半支为「无法确认 → 保留 pending → 人工核对，不重发」。新增元素只有 pending 状态菱形。
图注：一次超时先查证，再决定是否继续；查不到结果时保留疑点，而不是重复提交。

类比到这里有一个明确的断点：这不像普通消息队列可以靠「至少一次投递」自动重试。一次网页提交会创建真实会话并消耗账号额度，重复投递会改变对话本身；残余价值只在于「先记状态、再决定动作」这个顺序，不能把重发语义一起搬过来。

工具齐全以后，还差一个判断：什么任务适合走这条桥？

## 何时用，何时不用

三种任务比较适合：需要第二意见的规划或复审、能压缩成路径/符号/失败输出的最小证据、以及执行后带新证据继续追问的阶段性任务。宿主负责在本地执行和验证，Claude 的回复是外部建议，不是已核验事实；附件也必须由用户显式选择，且只接受 PNG 与 UTF-8 `.js`。

三种任务不适合：需要稳定公共 API 或服务端 SLA 的产品集成、要求无人值守自动触发的流水线、以及必须上传整个仓库或含敏感信息的原始日志。本项目不安装事件 hook，也不提供自动语义触发器；是否咨询由宿主在已有用户授权下判断。网页通道依赖 claude.ai 的页面结构，接口、选择器和文件协议都不是稳定公共契约。

| 关注点 | 网页通道 | 可选 HTTP 备用通道 |
|---|---|---|
| 会话真源 | 网页服务端历史 | 本地逐轮累积的文本历史 |
| 附件与产物 | 显式附件、可回拉受支持文件 | 纯文本，不接收附件或下载产物 |
| 不确定发送 | 回读历史后决定是否清除 pending | 无权威历史，须显式放弃未确认尝试 |
| 推理强度 | 由网页会话决定 | 按 `messages` / `chat` / `responses` 协议分别发字段 |
| 稳定性边界 | 网页实现可能变化 | 网关兼容性由操作者核验 |

表里没有「哪种通道更好」的统一答案：网页通道能处理会话与文件，却依赖页面；备用通道的请求形状更明确，却失去网页产物与权威历史。选择取决于这次任务是否需要附件、能否承受网页变化，以及发送不确定时是否愿意人工对账。

## 下一步

回到开头的支付回调：先只发错误分支的路径、失败输出和验收问题；拿到建议后在本地改代码、跑测试；再用同一别名补交新证据，读 transcript 核对回复是否完整。这条最小回路就是本项目的核心资产——它把「再问一次」从一次不可追踪的点击，变成授权、提交、查证、执行、复审五步。

若准备安装，按[中文安装指南](install.md)或 [English guide](install.en.md)从已校验的 Release 产物开始；需要逐项命令和边界时读[使用说明](usage.md)，需要核对 HTTP 字段时读[API 协议参考](api-protocols.md)。网页边界见[网页协议摘要](claude-web-protocol.md)，产物边界见[产物机制摘要](claude-design-protocol.md)。真实网页能否继续接受某条通道，仍要在你自己的浏览器与账号状态下核验；文档能交付的是可证伪的路径，不是替你完成这次核验。
